# 重构架构与实施原则

## 目标分层

| 层 | 职责 | 禁止事项 |
|---|---|---|
| 场景 | 固定关卡、碰撞、相机边界、明确锚点与静态美术。 | 将跨场景 Loading、BGM、服务或临时战斗对象常驻于场景。 |
| Bootstrap / Composition | 注册服务、启动过程和依赖组合。 | 承担具体 Boss、菜单或 UI 视觉逻辑。 |
| GF.Scene / 项目 SceneFlow | 请求、观察和完成场景切换。 | 由多个旧脚本同时直接 LoadScene。 |
| GF.UI | 页面层级、输入封锁、加载、菜单、HUD、暂停和结果。 | 动态拼装正式页面或在场景中预埋跨场景 UI。 |
| GF.Sound | BGM、UI、实体和环境音的分组与停止。 | 用临时场景 AudioSource 充当全局 BGM。 |
| GF.Entity / Pool | 技能、投射物、FX、可复用 HUD Item 等瞬时对象。 | 复用对象保留上次订阅、状态或不透明名称。 |
| 数据与资源 | UI 表、SoundGroup、EntityGroup、资源集合和 Prefab 标识。 | 在业务代码散落硬编码资源路径。 |

## 产品代码目录合同

`Assets/Game/Scripts/ColorTiming/` 采用 layer-first 结构，新增功能必须沿单向依赖扩展：

```text
Domain
  ↑
Application
  ↑
Presentation / Infrastructure
  ↑
Bootstrap
```

| 目录 | 所有权 |
|---|---|
| `Domain/` | 不引用 Unity/GF 的战斗、玩家、武器和 Boss 规则。 |
| `Application/` | `BattleSession`、命令、快照、用例和上层端口。 |
| `Presentation/` | Actor、技能、武器、UGUI、相机、世界交互等 Unity 表现。 |
| `Infrastructure/GF/` | GF.UI、GF.Sound、GF.Entity、GF.Setting 的具体端口实现。 |
| `Infrastructure/Unity/` | Unity Input、Time 等平台 API adapter。 |
| `Bootstrap/` | Procedure、CompositionRoot、SceneFlow、运行时组合和释放顺序。 |

项目 UI 固定放在 `Presentation/UI/`：

- `Forms/`：GF `UIFormBase` 派生页面。
- `Components/`：Prefab 子节点 View、Item、声音和局部序列组件。
- `Presenters/`：Application snapshot 到显示状态的转换。
- `Models/`：只属于表现层的值和枚举。
- `Contracts/`：UI 服务与消费方窄接口。

`Assets/Game/Scripts/UI/Core/` 只放 GF UI 通用基类、参数、Item 池和现有生成注册表；不得放 ColorTiming 业务 Form。代码目录不提交空骨架，Unity/GF 具体实现不得散落回 `Combat`、`Input/Adapters`、`Settings` 或 `Presentation/UI/Views`。

## 当前已批准的实现决策

1. 项目 Loading 为通用 GF.UI Prefab；UI 服务在产品切场景前打开，进度单调更新，切换完成后淡出关闭。
2. 框架 BuiltinView 的错误对话框仍保留；当前不显示其首次启动或场景切换的默认 Loading 进度条。
3. StartMenu BGM 由 MainMenu UIForm 经 GF.Sound 打开和停止，而不是 StartMenu 场景 `AudioSource`。
4. 所有运行时创建或复用对象由公共命名接口保证精确 `(Clone)` 后缀，避免 `(...)(Clone)` 累加。
5. 旧 `LoadScene_s` 在新 Loading 注册、资源收集与场景验证后移除；场景只保留静态内容。
6. 脚本移动必须通过 Unity AssetDatabase 并保留 `.meta` GUID；目录整理不得修改 Prefab/Scene 美术结构。
7. Player 是每场唯一、低频创建的场景生命周期对象：使用通用 Prefab 和 `BattlePlayerManager` 动态创建，不进入瞬态 GF.Entity 池；Scene 只声明出生位、Profile 和外部引用锚点。

## 批次实施方法

1. 在功能矩阵中选择相互依赖的 2～5 项功能。
2. 先建立或更新 OpenSpec：范围、行为规格、设计、任务和测试场景。
3. 先实现配置／Prefab／生命周期，再实现业务逻辑；Unity 序列化变更在停止 Play Mode 后验证。
4. 运行针对性 EditMode、PlayMode 和人工回归；更新证据入口与状态。
5. 未通过验证不得将功能标为“已验证”。
