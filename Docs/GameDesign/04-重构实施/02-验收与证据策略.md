# 验收与证据策略

## 验收层级

| 层级 | 回答的问题 | 证据 | 通过条件 |
|---|---|---|---|
| 编译与静态 | 代码和序列化能否被目标工程加载？ | Unity 编译结果、缺失脚本／引用审计、资源 GUID 审计。 | 无新增编译错误、Missing Script／Reference、无未解释 GUID。 |
| EditMode | 纯逻辑、映射和服务合同是否正确？ | XML/日志、针对性测试。 | 目标测试全过，并记录测试总数与日期。 |
| PlayMode | 生命周期、输入、场景、事件和运行时对象是否真实协作？ | PlayMode XML/日志、必要时单场景重跑。 | 目标测试完成；已知环境阻塞要单列，不得伪造通过。 |
| 人工回归 | 玩家能否感知到正确体验与视觉？ | 清单勾选、截图、录像时间戳。 | 按 StartMenu、Boss1、Boss2 的完整路径逐项通过。 |
| 视觉资源 | 目标画面是否保持源状态？ | 同状态源／目标截图，Spine/URP 材质审计。 | 无粉材质、Fallback、丢失资源或明显表现回归。 |

## 状态更新规则

- 任何失败都记录功能 ID、场景、操作、期望、实际和证据位置。
- 只要 PlayMode 或人工回归尚未完成，功能最多为“已实现待验收”。
- 批准修复必须按修复后的不变量测试，不要求复现源缺陷。
