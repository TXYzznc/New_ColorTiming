# Docs 建设方案讨论增量归档

> 状态：持续维护
> 用途：记录 Docs 建设过程中的已确认边界；不替代正式功能规格、验收清单或 OpenSpec。

## 2026-08-26｜第 1～2 轮决策检查点

### 已确认

1. 本项目当前没有新增玩法或产品需求。Docs 的功能范围以源项目实际具备的可观察行为为唯一验收基线。
2. 当前工程中缺失、未完成或待优化的行为必须被标记为重构待办或验证项；不得将推测性的未来玩法写成既定需求。
3. 每个功能文档采用可审计格式，至少记录：源项目行为、目标架构／重构方式、当前状态、验收方法，以及可追溯的证据位置。

### 影响

- 文档将服务于当前重构的范围控制、实现追踪与验收，不充当新的产品策划案。
- 总览、功能规格和状态总表之间使用功能 ID 与链接关联，避免同一规则在多处形成不一致的正式定义。

### 待确认

- Docs 是否完整采用参考项目的多层 GameDesign 目录，并如何处理暂时没有新增需求时的版本计划、路线图与想法库。

## 2026-08-28｜业务深层重构第 1～2 轮决策检查点

### 已确认

1. 本轮不是继续维护长期迁移适配层，而是先完成最终方案设计，再通过一次长任务整体实现业务重构。
2. 最终实现可以保留必要的薄 `MonoBehaviour` 表现适配器，用于接收序列化引用、Animation Event、Spine Event 和 UnityEvent；适配器不得保存核心业务状态。
3. `Legacy` 旧控制器、旧 `Weapon`、旧 `I_Damage` 和其他兼容业务模型不得作为最终架构继续存在。
4. 现有美术资源是受保护输入，必须复用且不得进行破坏式修改。允许在保留引用与内容完整性的前提下改名、移动路径或重新绑定新的表现适配器。

### 美术资源保护范围

- 贴图、Sprite、字体、音频、视频、材质、Shader、粒子、Spine 数据、Animator Controller、Animation Clip、Timeline 与 Prefab 的视觉内容。
- 129 条 Animation Event、19 条 UnityEvent、Spine Event 名称与时序，以及现有序列化资源引用。
- 已保存的源/目标视觉基线、GUID 映射和资源 SHA-256 审计结果。

### 实施影响

- 深层重构必须建立独立 OpenSpec change，并在实现前完成最终模块、依赖方向、数据所有权、资源事件边界、迁移表和回滚方案。
- 资源可以随一次性迁移重新绑定到新脚本，但不得要求重新制作美术内容，也不得通过重建资产造成 GUID、导入设置、动画曲线、事件或材质参数丢失。
- 验收必须同时包含业务回归、资源哈希/GUID 审计、Animation/Spine/UnityEvent 合同审计和视觉对照。

### 待确认

- 本轮验收是否要求所有自动化、资源合同和三场景人工回归一次性全部通过，才能删除旧业务实现并认定重构完成。

## 2026-08-29｜运行时性能优化第 1～2 轮决策检查点

### 已确认

1. 优化目标是在不改变现有画面、玩法和资源内容的前提下，同时降低峰值内存、稳定 60 FPS 并缩短场景加载；允许重构运行时实现。
2. 本轮采用 A+B 组合：场景级公共资源常驻，当前武器／攻击级动画、贴图和特效按需加载与释放；同时只对通过画面验收的资源实施 Importer／压缩优化。B 是 A 的配套手段，不得以单纯压缩替代加载边界重构。
3. Addressables 不进入本轮。项目继续使用既有 GF Resource／AssetBundle 体系；只有未来出现远程内容分发、DLC 或热更新的明确需求时，才以独立变更评估 Addressables。
3. 不继续使用当前 Unity 2022 原生 SpriteAtlas 打包路径；此前试点已发生编辑器原生纹理压缩崩溃，后续方案必须绕开该路径。

### 已知依据

- 2026-08-28 的 Editor 采样显示 Boss1、Boss2 的纹理与总内存远高于 StartMenu；Hero 单一 AnimatorController 对全部武器逐帧动画的直接引用是主要常驻风险。
- 本轮需把“资源可按需加载”与 Animation Event、Animator／Spine、GF Entity 生命周期和场景卸载共同验证，不能仅以资源被卸载作为通过条件。

### 待确认

- 允许在武器即将生成时进行后台预热；拾取与首次攻击路径不得进行同步加载或显示 Loading。
- 验收以 Windows Development Player、1920×1080 为准：Boss 战稳定 60 FPS，武器生成／拾取／首次攻击无可感知卡顿，Boss2 峰值纹理内存目标不高于 1 GB。
- 采用 A+B 两阶段 Animator 改造：先新增基础动作与武器专用的运行时 Controller／Prefab 组合并验证等价，再直接精简原 Hero AnimatorController 的依赖。允许重绑运行时引用和修改 Controller；原始贴图、Animation Clip、Spine 数据以及 Animation／Spine／UnityEvent 的名称和时机保持不变。
- 每阶段都必须保留可独立回退点，并通过资源依赖审计、动画事件合同和完整 Player 回归后，才可进入下一阶段。

## 2026-08-29｜武器生成配置化第 1～2 轮决策检查点

### 已确认

1. 武器颜色与类型组合是受现有美术资源约束的内容能力；任何生成器不得假设所有颜色与所有类型均可组合。
2. Boss、未来小怪或其他生成场景只引用统一的武器生成规则 ID，由 `ColorTimingWeaponSpawnRuleTable` 定义生成间隔、同屏上限、保底阈值和允许的武器组合；不得再通过 `Boss1()`／`Boss2()` 代码分支决定内容。早期采用的 `WeaponSpawnRuleAsset` 已被本轮表驱动重构取代。
3. 为保持当前产品行为，初始规则资产保留 Boss1 的 9 组（红/绿/紫 × 剪刀/锤子/炸弹）与 Boss2 的 12 组（四色 × 戒刀/斧头/飞机）；新增内容可新建或复用规则资产，无需修改运行时代码。

### 验收

- 生成策略只从规则资产列出的 `WeaponIdentity` 条目中选择；若当前弱点颜色没有可用美术组合，不触发无法生成的保底，而从规则内随机选择。
- Boss1、Boss2 场景各自持有规则资产引用；两个既有策略与库存 EditMode 测试均通过。

## 2026-08-28｜业务深层重构第 3～4 轮决策检查点

### 已确认：资源保护边界

1. 原始美术资源内容视为只读，包括纹理、Sprite、字体、音频、视频、材质、Shader、粒子、Spine、Animator、AnimationClip 和 Timeline；允许迁移或改名，但必须保留 `.meta` 与 GUID 连续性。
2. 场景与 Prefab 允许替换业务脚本、重绑序列化字段以及调整纯功能性节点，但不得破坏视觉层级、RectTransform、渲染顺序、美术资源引用、事件名称与事件时机。
3. 现有 Animation Event、UnityEvent 与 Spine Event 由薄适配器承接。适配器只负责把引擎回调转换为业务命令或表现事件，不持有战斗核心状态。
4. 资源保护验收以清单、GUID、依赖、序列化事件和自动化契约为主，不以大量截图为主要分析手段；最终画面、手感和音效由制作人实机验收。

### 已确认：完成判定

1. 源项目功能清单中的全部功能 ID 均须有新实现或明确的保留说明，除已批准修复项外不得产生未授权行为变化。
2. Unity 编译必须为 0 error；EditMode、PlayMode 和 StartMenu/Boss1/Boss2 生命周期契约必须通过。
3. 受保护资源必须通过路径、GUID、依赖、导入设置与内容完整性审计；Prefab/Scene 的允许变化必须可解释并可追溯。
4. 129 个 Animation Event、19 个 UnityEvent 以及全部 Spine Event 接收与退订契约必须被覆盖。
5. 自动化、资源和事件契约通过后，在同一次长任务中删除被新架构替代的旧业务实现，不保留长期双轨业务逻辑。
6. 截图仅作为可选辅助证据，不作为自动化阶段的阻塞项；最终视觉回归由制作人验收，发现问题后继续修复，不通过降低标准换取完成状态。

### 决策状态

- 目标：已确认。
- 总体方案：已确认，完整设计后一次性实施。
- 资源边界：已确认，复用且不破坏既有美术资源。
- 验收门槛：已确认，契约与自动化优先、人工视觉验收收尾。
- 框架边界：已确认，业务重构不修改 `Assets/Game/ScriptsBuiltin/`。

## 2026-08-31｜重复实现与错误枚举化审计第 1～2 轮决策检查点

### 已确认

1. 审计范围覆盖当前项目全部内容，包括业务脚本、Prefab、Scene、配置、Editor 工具、测试与 `Assets/Game/ScriptsBuiltin/` 框架核心；本轮只读分析，不因纳入审计范围而自动授权修改框架核心。
2. 只有在结构、生命周期和核心算法一致，仅因 Boss、关卡、武器、UI 类型或其他枚举值不同而复制实现时，才判定为“错误枚举化”。
3. 具有不同状态机、时序、资源所有权、性能边界或引擎回调契约的实现，即使局部代码相似，也不得仅为减少文件数量而强行合并。
4. 对可能可以合并但证据不足的实现，单列为“待决策候选”，记录相同点、差异点、风险和推荐方案，由制作人确认后再决定是否实施。

### 当前已确认案例

- `BattleHud` 的 Boss 血条不应区分 `Slot_Boss1HP` 与 `Slot_Boss2HP`。所有 Boss 使用一致的血条布局和 Item 表现，应统一为一个 `Slot_BossHP` 与一个通用 Boss 血条 View；Boss 类型只作为提示内容或数据参数，不复制容器和控制器。

### 待确认

- 审计报告是否同时给出可直接实施的合并优先级、迁移风险与验证范围，并在报告确认后建立一个 OpenSpec change 统一修复。

## 2026-08-31｜Player 动态生命周期决策检查点

### 已确认

1. Boss1、Boss2 场景不再静态保存 Hero；Player 必须由动态 `BattleRuntimeContext (Clone)` 所有的专职管理器创建、配置和释放。
2. 两关使用一个能力完整的 `Player.prefab`，运行时实例保留 `Player(Clone)` 名称；不得为了关卡差异维护 Boss1/Boss2 两个 Player Prefab。
3. Boss1/Boss2 原有移动音效集合与镜头参数存在真实差异，分别迁入 Player Scene Profile，不允许用一个场景的数据覆盖另一个场景。
4. Scene 只保存 Player Prefab/Profile、出生位置、WeaponSpawner、Cinemachine、Boss Target 与 DeathSequence 等显式锚点；动态生成后一次性注入，不使用名称查找。
5. Player 每场只创建一次且生命周期等同战斗场景，不进入瞬态 GF.Entity 池；技能、武器和特效继续由 GF.Entity 管理。

### 验收边界

- 两个 Scene 的静态 Hero 和 Cinemachine/DeathSequence 旧引用清零。
- Boss1/Boss2 各只存在一个动态 `Player(Clone)`；死亡重载后旧实例释放并创建新的满血实例。
- 原角色美术、Animator、碰撞、挂点、技能 Prefab 和 AudioClip 内容不做破坏式修改。
