## Context

当前项目已经接入 FSR、中文 Git 描述规则和第一版多窗口协作模板，但尚未有专职 Git 集成窗口；当前模板仍要求专业窗口获得 Git 索引锁后自行提交。用户已确认近期将引入客户端、技术美术、测试等长期窗口，因此需要在不覆盖 ColorTiming 业务改动的前提下同步外部框架的协作增量。

## Goals / Non-Goals

**Goals:**

- 建立可由用户创建和注册的 `git-integration` 角色，作为共享工作树的唯一常规暂存／提交执行者。
- 将提交请求的输入、拒绝条件、明确暂存、中文提交和异常升级写为可审计合同。
- 将专业窗口自治、制作人强制升级边界与 Git 集成路由同步到现有 Dispatch 文档。
- 使纯度审计将新文档纳入完整性检查，并安全读取 UTF-8 BOM。
- 初始化既有 FSR 子模块，不变更其已锁定的版本、依赖或项目代码。

**Non-Goals:**

- 不从外部仓库合并提交历史、OpenSpec 历史、框架基线业务外内容或任何资产。
- 不暂存、提交、清理或改写当前未提交的 ColorTiming 工作树。
- 不建立真实 threadId／hostId 注册表，也不创建用户可见线程；这由用户后续按初始化指南完成。

## Decisions

### 1. 将 Git 集成定义为无业务技能的专职角色

新增 `.claude/agents/git-integration.md`，只授予读取、差异检查与 Git 命令所需工具，不配置产品领域 SKILL；`.codex/agents/git-integration.toml` 仅由同步脚本生成。

**备选方案：**继续由每个专业窗口在短锁下提交。
**未采用原因：**多个长期窗口共享工作树时，索引归属和提交范围无法集中审计。

### 2. 原子同步协作规则，不复制外部仓库历史

同步的最小原子包括角色源、GitIntegration 合同、所有引用该合同的 Dispatch 模板／入口、入口指令、纯度审计及回归测试。仅导入其中的通用规则；保留当前项目的业务 Docs、变更和配置。

**备选方案：**仅添加 GitIntegration 文档。
**未采用原因：**入口、模板和审计仍会指向旧索引锁模式，形成两套冲突规则。

### 3. FSR 只做本机就绪修复

当前项目的 manifest、lock、文档和子模块指针已与参考仓库一致；仅初始化缺失工作树内容并验证，不复制包或改动指针。

## Risks / Trade-offs

- [专职窗口未注册即被规则要求提交] → 文档明确真实注册表由用户初始化；实际需要提交时先创建／注册该窗口。
- [当前未提交改动被误带入] → 本变更不执行 Git 暂存／提交；GitIntegration 合同禁止全量或通配暂存。
- [手动覆盖生成 TOML] → 仅编辑 `.claude/agents`，随后使用 `tools/sync-agents.py` 生成并用 `--check` 验证。
- [子模块网络或凭据失败] → 保留配置不变，报告初始化失败，不尝试替换来源或版本。

## Migration Plan

1. 添加角色源、白名单条目及 Git 集成合同。
2. 对现有 Dispatch 文档应用所需的自治和 Git 路由增量，更新入口指令与 producer 角色。
3. 更新纯度审计与测试，生成 Codex agent 配置。
4. 初始化并验证 FSR 子模块，运行 agent 同步检查、审计测试和框架纯度审计。

**Rollback:** 本变更仅新增或修改协作文档、角色元数据、Python 审计和 FSR 子模块工作树；可按本 OpenSpec 的精确文件回退，不影响 `Assets/` 或现有重构文件。
