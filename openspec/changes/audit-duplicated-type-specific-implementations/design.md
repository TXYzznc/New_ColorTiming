# 设计：类型枚举化重复实现审计

## 判定模型

每组候选从以下维度比较：输入数据、状态机、生命周期、核心算法、资源所有权、布局／视觉结构、引擎回调契约和性能边界。

- **确定错误**：上述核心维度一致，仅类型名、枚举值、提示文本或配置数据不同，却复制了脚本、Prefab 或分支。
- **待决策候选**：大部分维度一致，但仍有尚未证明可配置化的行为差异或兼容风险。
- **合理独立实现**：至少存在一个真实独立的状态机、时序、资源生命周期、性能边界或引擎契约。

代码相似度只用于发现候选，不作为最终判定依据。

## 审计路径

1. 通过文件名、类型名、相邻目录、继承关系、重复方法和枚举／switch 分支发现候选。
2. 追踪候选在 Prefab、Scene、配置、事件和测试中的真实使用方式。
3. 对照源项目和 OpenSpec，判断差异来自产品需求还是迁移实现。
4. 对每项给出保留、配置化、策略化、组合化或合并为通用组件的建议。
5. 不确定项保持候选状态，由制作人决策。

## 边界

- 审计覆盖 `Assets/Game`、`ProjectSettings`、`Docs` 和 `openspec` 中与运行时及工具行为有关的内容。
- `ScriptsBuiltin` 纳入审计，但发现问题不等于授权修改框架核心。
- 不把 GF 框架针对不同底层组件定义的必要 Helper、不同序列化类型或平台实现误判为业务枚举化。
- 不破坏既有美术资源、GUID、Animation Event、Spine Event 或 UnityEvent。

## 报告结构

每项记录 ID、分类、位置、重复结构、真实差异、判定依据、推荐方案、迁移风险、验证范围和优先级。
