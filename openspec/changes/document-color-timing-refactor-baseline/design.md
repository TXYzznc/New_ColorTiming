## Context

ColorTiming 正在从源工程迁移至 GF_X。现有迁移 OpenSpec evidence 已积累场景、脚本、资源、动画和测试证据，但它不是长期可读的项目 Docs。用户已确认：不定义新玩法；以源工程可观察功能为基线；每个功能必须可追溯至重构方式与验收依据；目录必须能承接未来需求。

## Goals / Non-Goals

**Goals:**

- 建立分层 Docs：稳定的跨系统基线、按领域拆分的功能规格、玩家可见流程、重构实施索引和设计管理。
- 使用稳定功能 ID（`CT-<领域>-<序号>`）连接系统文档、状态表、验收清单和 OpenSpec。
- 让每项功能以“源行为 → 目标重构 → 状态 → 验收/证据”的同一格式可审计。
- 为未来需求保留入口、状态语义和变更流程，而不预先定义未来玩法。

**Non-Goals:**

- 不修改运行时代码、场景、Prefab、数据表、资源或既有测试。
- 不复制源工程或历史审计的所有原始 CSV/日志到 `Docs`。
- 不把待讨论的玩法、数值或美术方向写成当前项目承诺。

## Decisions

### 1. 采用参考项目的层级，但以重构为中心

`GameDesign` 保留“核心框架、系统设计、玩家体验、第一版、设计管理”的阅读结构；其中“第一版”改为“重构实施”，记录当前唯一需求的执行和验收。`Development` 保留跨项目技术规范，现有 GF UI 标准原样作为该层的专门规范。

**备选方案：**仅维护一份长验收清单。
**未采用原因：**读者无法按系统理解目标架构，后续新增需求也难以定位影响范围。

### 2. 文档定义功能合同，不重复原始证据

系统文档保留足以实现和验收的行为描述；每项功能以 ID 链接至迁移 OpenSpec evidence 中的 `source-feature-acceptance-checklist.md` 和相应审计文件。经筛选的验收证据放在所属 OpenSpec 的 `evidence/`，可再生成的原始流水不保留。

**备选方案：**把所有历史证据复制到 Docs。
**未采用原因：**会产生双份事实来源并使维护成本上升。

### 3. 使用四态重构状态和扩展入口

状态仅使用“已验证、已实现待验收、实施中、待实施/待确认”；未来功能先进入开放问题或需求入口，经过决策、OpenSpec、功能规格和验收后才成为基线。未确认需求不得出现在“已具备功能”中。

**备选方案：**把当前所有记录都标为完成。
**未采用原因：**现有 PlayMode 全量验证未完成，且源功能迁移仍在进行。

## Risks / Trade-offs

- [源行为存在未覆盖细节] → 系统文档将明确链接权威验收清单，并要求新增差异先登记后更新合同。
- [文档与代码状态漂移] → 每个重构批次在 OpenSpec 完成时同步状态表、受影响功能页和验收证据。
- [未来需求污染当前基线] → 新需求仅进入需求入口，未确认前不修改功能规格或验收标准。

## Migration Plan

1. 建立 Docs 目录、总览、状态表与术语/决策管理文件。
2. 按启动、玩家、武器、Boss、HUD、音频世界、资源渲染等领域写入功能基线与重构方式。
3. 建立重构功能矩阵与验收入口，链接已有迁移 OpenSpec evidence。
4. 验证链接、功能 ID 覆盖与 OpenSpec 格式；后续每个变更按该入口维护。

**Rollback:** Docs 为新增、无运行时副作用的文件；如结构不合适，可只回退本次新增 Docs 和本 OpenSpec 变更，不影响现有重构实现。
