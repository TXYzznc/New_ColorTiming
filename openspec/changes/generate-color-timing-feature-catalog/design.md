## Context

ColorTiming 的功能信息目前分散在业务代码、GF UI 表单、场景与预制体、数据表、测试、Docs 以及多个历史 OpenSpec change 中。清单面向策划、程序、美术和后续新岗位，用于快速理解“功能是什么、效果如何、为何这样设计、当前是否可靠、以后是否处理”，而不是承担排期或人员管理。

## Goals / Non-Goals

**Goals:**

- 以玩家体验和业务规则为主视角，完整反推出当前项目已有功能。
- 每项功能具有足够具体的规则、效果和设计原因，可供后续设计引用。
- 将代码存在与验证结论分开，避免把“能找到实现”误写成“已经验收正常”。
- 显式记录歧义、缺陷、待讨论方案和已通过待实现事项。
- 交付可直接上传飞书的 `.xlsx` 工作簿。

**Non-Goals:**

- 不修改任何运行时代码、场景、预制体、配置或美术资源。
- 不替团队替代尚未做出的玩法和美术决策。
- 不把负责人、工期、成本等项目排期字段塞入功能认知清单。

## Decisions

1. 每行记录一个可独立说明和验收的具体功能；模块仅用于分类，不以“大系统”代替具体能力。
2. 团队主表字段固定为：功能编号、所属内容、功能名称、玩家看到/感受到什么、为什么需要它、现在是什么状态、目前有什么问题、以后怎么处理、处理状态。
3. 当前情况描述证据强度与实现结果；后续状态使用固定枚举：无需处理、待讨论、讨论中、已通过待实现、处理中、待验收、已完成、暂缓、不再采用。
4. 工作簿按阅读对象分层：团队功能清单、待讨论事项、制作注意事项、填写说明面向策划和美术；技术依据放在最后一页供程序查阅。待讨论事项仍从完整审计结果中提取，不创建第二份独立事实源。
5. 团队页面使用玩家体验和制作语言，类名、接口名、测试名与代码路径只保留在技术依据页。
6. 审计优先级为：运行时代码和资源引用事实 > 自动化测试与验证证据 > 当前 OpenSpec/Docs 记录 > 历史意图。无法从仓库确认的内容必须标为歧义，不自行推测。

## Risks / Trade-offs

- [静态审计无法证明所有画面和手感正常] → 当前情况明确标注证据边界，并将需要人工体验的项目设为“待验收”或“待讨论”。
- [功能粒度过细导致表格难读] → 以能够独立说明规则或单独出现问题为拆分标准，不按每个方法或组件建行。
- [历史 OpenSpec 与现状可能不一致] → 以当前代码、资源和测试为主，历史记录仅用于解释设计目的与遗留事项。
- [飞书导入可能改变样式] → 使用标准表格、冻结表头、筛选和普通数据验证，不依赖复杂宏或专有功能。
